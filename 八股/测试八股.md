# 测试

测试总的来说可以分为两大类：功能测试和非功能测试。

- 功能测试类型包括：单元测试、集成测试、系统测试、健全性测试、冒烟测试、接口测试、回归测试、Beta/验收测试。
- 非功能性测试类型包括：性能测试、负载测试、压力测试、容量测试、安全测试、恢复测试、可靠性测试、可用性测试、一致性测试、本地化测试。

## 什么是软件测试

测试是一种通过人工或自动手段运行、评估软件系统过程， 目的是验证软件是否满足预期的功能需求、性能安全性和用户体验， 并发现其中的缺陷。 软件测试是为了发现错误， 提高软件质量

## 软件测试的原则

- **测试证明缺陷的存在 (Testing shows presence of defects)**：测试是为了证明软件中存在缺陷，而不是为了证明软件中没有缺陷。
- **穷尽测试是不可能的 (Exhaustive testing is impossible)**：由于输入、操作组合太多，无法进行全量测试。应基于风险和优先级进行策略化测试。
- **尽早测试 (Early testing)**：测试应在软件开发生命周期的早期阶段就开始（如需求评审），缺陷发现越早，修复成本越低。
- **缺陷群聚 (Defect clustering)**：缺陷通常遵循“二八定律”，即 80% 的缺陷通常集中在 20% 的核心模块中。
- **杀虫剂悖论 (Pesticide paradox)**：如果重复使用相同的测试用例，它们将不再发现新缺陷。测试用例需要定期评估和更新。
- **测试依赖于上下文 (Testing is context dependent)**：不同类型的软件（如电商 App 与银行系统）需要采用不同的测试策略和强度。
- **“没有错误”的谬论 (Absence-of-errors fallacy)**：即使测试未发现缺陷，也不意味着软件能够满足用户需求或可以立即发布。

## 测试计划通常包含哪些内容

- 项目背景与目标
- 测试范围
- 测试策略与方法：如功能测试、性能测试、安全性测试、自动化测试等。
- 进度安排：明确测试各阶段的时间安排，包括用例设计、执行、回归测试和报告产出。
- 资源规划：明确人力资源分工（谁负责什么）
- 风险评估与应对：预判潜在的测试风险（如人员短缺、环境不稳定、时间紧迫）、制定相应的缓解预案。
- 准入与准出标准：定义测试开始的条件（例如：冒烟测试通过）。定义测试结束和发布的条件（例如：严重 Bug 清零）。
- 交付物：列出测试过程中产生的文档，如测试计划书、测试用例、测试总结报告、缺陷记录等。

## bug 的生命周期

BUG 的生命周期，就是一个 BUG 被发现到这个 BUG 被[关闭](https://zhida.zhihu.com/search?content_id=111161076&content_type=Article&match_order=1&q=关闭&zhida_source=entity)的过程。发现 BUG-->提交 BUG-->指派 BUG-->开发确认 BUG-->开发去修复 BUG-->回归验证 BUG-->是否通过验证-->关闭 BUG

## bug 的优先级

**常见 Bug 优先级划分 (P0 最高，P3 最低):**

- **P0 (Critical/Immediate):** 致命错误（如崩溃、死锁、数据丢失）。系统无法运行，需立刻修复。
- **P1 (High/Urgent):** 严重问题。核心功能不可用、影响测试进度或高风险安全问题。
- **P2 (Medium/Normal):** 普通问题。主要功能受损但可绕过，或功能实现不完整。
- **P3 (Low/Minor):** 轻微问题。界面错位、错别字、提示语不明确等不影响功能的问题

## Bug 优先级和严重程度有什么区别？

**优先级是从公司运营角度(人力配置、资金投入等)出发，而严重程度是从纯技术角度出发**。

- bug 的标题简介明了

- **重现步骤**：bug 的步骤符合自己在测试中的步骤

- 说明是在哪个环境中发现的

- 预期结果和实际结果，截图，日志

- 严重程度

## 测试点和测试用例的区别

测试用例包括测试输入、执行条件和预期结果

测试点是指测试功能点， 是测试场景的一种描述， 不包含具体测试数据

## 测试左移和测试右移

测试左移：提测之前的测试，例如代码单元测试

测试右移：发布验证后的测试，例如对于用户反馈问题的处理

测试左移的本质思想是尽早发现不合理的地方，减少后续缺陷

测试右移是指版本上线后需要持续关注线上监控和预警，及时发现问题并跟进解决，将影响范围降到最低。

## 如何保证测试覆盖率？

尽量做到覆盖需求和功能，确定好要测试的业务流程与功能点，运用流程图法、等价类划分法、边界值法针对每一个功能设计测试用例，覆盖正向、逆向，以及做好非功能测试

## 回归测试怎么做

常见的回归测试有增量回归测试和全量回归测试

增量回归测试仅对本次迭代中代码变更部分执行测试，而非整个应用

全量回归测试则是重新执行*整个测试集*

## 冒烟测试

在全面测试开始前，优先检验软件的核心功能是否正常运行（即“主流程是否跑得通”），以排除致命缺陷，避免浪费后续的深度测试时间

**名称由来**：源于硬件行业，指设备通电后若出现短路导致冒烟，即表明有严重故障。在软件开发中，它形象地借用了这一概念来表示对版本的“健康检查”。

## 常见测试类型

#### 功能（黑盒）测试

不考虑内部实现，对软件进行功能测试

#### 等价类划分

<img src="https://i-blog.csdnimg.cn/blog_migrate/3f83beb5a77bad074c291480c8855548.png#pic_center" alt="在这里插入图片描述" style="zoom:67%;" />

- 有效等价类：是指对于程序的规格说明来说是合理的、有意义的输入数据构成的集合。利用有效等价类可检验程序是否实现了规格说明中所规定的功能需求。
- 无效等价类：与有效等价类的定义相反，是指对程序的规格说明是不合理的或无意义的输入数据所构成的集合。他能检验程序在不符合规则的数据输入下，是否会有异常（无效等价类至少应该有一个，也可能有多个，视情况而定）

#### 边界值分析法

1.边界值分析法也是一种典型的黑盒测试方法，其主要的测试点 是对“输入”或“输出”的“边界”值进行测试 2.通常**边界值分析法是作为对等价类划分法的补充**，这种情况下，其测试用例来自等价类的边界

#### 因果图分析法

等价类划分法和边界值分析法它们都是着重考虑输入条件，但是未考虑输入条件之间的联系、相互结合等。因此，必须考虑采用一种适合于描述对于多种条件的组合，相应产生多个动作的形式来考虑设计测试用例，这就需要利用因果图分析法（逻辑模型）

#### 错误推断法

根据以往的测试经验和对系统内部知识的了解，列出系统中各种可能有的错误和容易发生错误的特殊情况，再根据它们来设计测试用例。

### 白盒测试

全面了解程序内部逻辑结构、对所有逻辑路径进行测试。

6 种白盒测试方法：（强度由低到高）

- 语句覆盖：设计若干个测试用例，运行被测程序，使得每一可执行语句至少执行一次。
- 判定覆盖：每个判定的 True 和 False 至少执行一次。
- 条件覆盖：判定中每个“子条件”的 True 和 False 都出现过。
- 判定条件覆盖：同时满足判定覆盖、条件覆盖。
- 条件组合覆盖：判定中所有子条件的所有组合都必须测试。（如果有 n 个子条件：需要测试 2^n 种组合。）
- 路径覆盖：每条可能执行到的路径至少执行一次；通常不可实现

### 灰盒测试

灰盒测试则介于两者之间，测试人员会了解部分程序的内部结构和代码，但并不需要像白盒测试那样深入。灰盒测试方法旨在提供一种更全面，更深层次的测试。例如，关注系统之间的交互

在灰盒测试中，我们可能会进行以下测试：

1. 添加一个商品到购物车，然后检查库存系统是否正确地减少了相应的库存数量。这需要我们知道购物车和库存系统是如何交互的，但并不需要我们知道库存系统的具体实现。
2. 删除购物车中的商品，然后检查是否正确地从总价中减去了商品的价格。这需要我们知道购物车和价格系统是如何交互的，但并不需要我们知道价格系统的具体实现。
3. 更改购物车中的商品数量，然后检查是否正确地更新了总价和库存。这同样需要我们知道购物车是如何与其他系统交互的。

灰盒测试的优点是，它可以提供比黑盒测试更深入的测试，而且比白盒测试更高效。

### 接口测试

**接口测试是什么** ：是对系统与系统间的接口进行测试，主要是校验接口的**输入参数**，**业务逻辑以及返回数据**是否正确 。

-**接口性能测试** ：测试接口的响应速度 ，吞吐量 ，并发用户数 ，验证它们是否符合标准

-**接口安全测试** ：测试接口关键字段是否加密 ，存入数据库的关键字段是否加密 ；是否存在 SQL 注入 。

-**接口功能测试** ：输入参数的数据 ，业务逻辑判断 ，返回数据正确性 。

-**输入参数校验** ：必填项和非必填项的单独校验，组合校验 ；必填项输入的数据类型、为空 、数据异常 、业务数据不合理 。

-**业务逻辑校验** ：这个没的说，你必须理解每个接口的业务是什么 ？它的作用是什么 ？

-**返回数据校验** ：它一般是 json 格式，返回数据主要分两部分 ，**代表成功状态的一部分和业务数据的一部分** ，成功状态就两个参数 ，业务状态码，如 errno , 业务消息 ，如：errmsg ; 业务数据才是我们测试的重点 ，**它一般又放在一个大的子 json 里，里面全是它的业务数据 。而这个 json 的键名也比较好识别 ，可能用 data 、response 进行标识** 。

常用工具：postman 、jmeter

### 自动化测试

使用软件工具和脚本来执行测试任务。它可以自动化执行测试用例、生成测试报告和进行结果分析

自动化测试框架和工具，例如 Selenium、Appium 和 JUnit。

持续集成和持续交付(CI/CD)：在应用[开发阶段](https://zhida.zhihu.com/search?content_id=213750914&content_type=Article&match_order=1&q=开发阶段&zhida_source=entity)引入自动化来频繁向客户交付应用的方法

- 持续集成：新提交代码在合并前，需要先进行自动化测试。即，在源代码变更后自动检测、拉取、构建和（在大多数情况下）进行单元测试的过程
- 持续交付：完成自动化测试后，自动将已验证的代码发布到服务器，可随时部署到生产环境

## 测试用例设计方法有哪些

1、场景法

每一个用户可以进行交互的东西都要测，比如输入框，按钮等；

2、流程去考虑

先输入手机号，点击获取验证码，输入验证码，点击登录。登录成功，这是基本流

登录失败（验证码错误），备选流

3、边界值

6-10 位，那就测 5,6,10,11 就够了

4、等价类

7 和 6 是同一等价类，测了 6 就不用测 7 了

5、非功能场景

网络情况，兼容性（IOS，Android），接口（涉及到手机号要验证是否加密），数据校验（去数据库看数据是否落地），UI，权限，断线重连

6、业务

验证码限制发送次数

## 测试数据如何构造

1.**通过 GUI 构造测试数据**：直接在客户端操作，产生测试数据，准确性高，但手工测试效率不高。**适用场景**：少量数据、初期功能探索或难以通过自动化手段实现的操作。

2.**调用 API 接口**，并结合 jmeter、postman 等工具，就可以绕过客户端批量构造测试数据，效率较高。**适用场景**：批量自动化测试、接口测试、需要频繁重置环境的场景。

3.**数据库直接写入/操作**，可绕过 API 接口直接调用数据库语句，实现海量数据的构造，效率很高；但若代码改动，维护成本也高。此外，像 Redis 这样的[缓存数据库](https://zhida.zhihu.com/search?content_id=113310233&content_type=Article&match_order=1&q=缓存数据库&zhida_source=entity)，是无法批量操作的，要在 Redis 中构造海量测试数据，还是需要通过调用 API 接口来实现。**适用场景**：大规模数据初始化、性能测试、复杂状态构造。

4.**抓包直接修改数据**：例如，我们要测试客户端上 100+消息时的表现，这时候就可以抓包后打断点，把消息数修改成 100+即可。

5.**线上数据脱敏导入**：将生产环境数据脱敏后导入测试环境，数据最真实，覆盖场景最全。**适用场景**：真实业务场景模拟

基于测试数据的特性，我们又把测试数据分为**on-the-fly（即用即建）**和**out-of-box（开箱即用）**两种。

- on-the-fly 是执行测试用例时需要实时创建的数据，这类数据我们很难事先准备，一般被称为“活水数据”（不稳定，经常改变的数据），例如我们执行下单的用例，订单号是实时生成而不是事先准备的，因此往往采用 GUI 来构造测试数据。
- out-of-box 是执行测试用例时可以事先准备、开箱即用的数据，例如我们下单前需要有很多商品，那么这些商品数据是可以事先准备的，一般被称为“死水数据”（稳定，几乎不改变的数据），因此可以采用 API、数据库操作或 API 和数据库操作结合的方式来构造测试数据。

## Fiddler/Charles 的抓包原理

原理：中间人攻击（MITM），将自己设置为系统的 https 代理服务器，拦截并转发客户端与服务器之间的所有通信数据，从而实现对流量的捕获、查看、修改和重发

对于 http，直接拦截并明文显示；

对于 https，涉及到解密加密：

![img](https://i-blog.csdnimg.cn/blog_migrate/3b10a6a95798823c485bb24a141df6ab.png)

（1） 客户端请求建立 HTTPS 链接，发送客户端支持的加密协议 及版本列表等信息给服务器端。

（2） Fiddler 接受客户端请求，并伪装成客户端向 WEB 服务器发送相同的请求。

（3） WEB 服务器收到 Fiddler 的请求以后，从请求中筛选合适的加密协议。并返回服务器 CA 证书，证书中包括公钥 信息。

（4）Fiddler 收到 WEB 服务器的响应后，保存服务器证书并伪造一个自签名的 CA 证书，伪装成服务器，把该证书下发给客户端。

（5）客户端验证证书合法性。（Fiddler 能否抓取到 HTTPS 报文关键看这一步）

（6）客户端生产对称密钥，并使用伪造的公钥证书进行加密，发送给服务器。

（7）Fiddler 拦截客户端的请求以后，使用伪造的私钥解密该报文，获取对称加密秘钥，并使用真正服务器证书中带的公钥加密该对称密钥发送给 WEB 服务器。(此时对称密钥已经泄露了，以后可以使用该秘钥解密客户端和服务器端传输的数据)

（8）WEB 服务器接收到客户端发送的加密的对称密钥后，使用私钥解密，并使用对称密钥加密测试数据传给客户端。

（9）Fiddler 使用前面获取的对称密钥解密报文。

（10）客户端验证数据无误以后，HTTPS 连接就建立完成，客户端开始向服务器发送使用对称密钥加密的业务数据。

（11）Fiddler 使用前面获取的对称密钥解密客户端发送的数据，并重新加密转发给服务器端。

Charles 与 Fiddler 基本一致，但为了巩固记忆，再贴一遍原理图：

![img](https://i-blog.csdnimg.cn/blog_migrate/d087baa8e35054d35c39dec170de6f77.png)

1. 客户端向服务器发起 HTTPS 请求
2. Charles 拦截客户端的请求，伪装成客户端向服务器进行请求
3. 服务器向“客户端”（实际上是 Charles）返回服务器的 CA 证书
4. Charles 拦截服务器的响应，获取服务器证书公钥，然后自己制作一张证书，将服务器证书替换后发送给客户端。
5. 客户端接收到“服务器”（实际上是 Charles）的证书后，生成一个对称密钥，用 Charles 的公钥加密，发送给“服务器”（Charles）
6. Charles 拦截客户端的响应，用自己的私钥解密对称密钥(Charles 拿到了对称密钥)，然后用服务器证书公钥加密，发送给服务器。
7. 服务器用自己的私钥解密对称密钥，向“客户端”（Charles）发送响应
8. Charles 拦截服务器的响应，替换成自己的证书后发送给客户端
9. 至此，连接建立，Charles 拿到了 服务器证书的公钥 和 客户端与服务器协商的对称密钥，之后就可以解密或者修改加密的报文了。

## 性能/压力测试是怎么做的

性能测试：验证系统在**正常负载**下的响应时间和吞吐能力。

负载测试：逐步增加并发，找到系统可稳定运行的最大容量。

压力测试：超过系统设计上限，观察是否崩溃、自恢复，目标是测试系统极限和容错能力。

稳定性测试（Soak Testing）：长时间持续运行（几小时到几天），目标是测试是否内存泄漏、连接泄漏。

## 性能指标有哪些（QPS 是什么）

![img](https://pica.zhimg.com/v2-fcfde708b6932cc0bd65a64cd528748a_1440w.jpg)

QPS：每秒请求数。信息检索系统（例如搜索引擎或数据库）在一秒钟内接收到的搜索流量

TPS：每秒事务。一个事务是指客户端向服务器发送请求然后服务器做出响应的过程。

RT（Response-time）响应时间：执行一个请求从开始到最后收到响应数据所花费的总体时间，即从客户端发起请求到收到服务器响应结果的时间。该请求可以是任何东西，从内存获取，磁盘 IO，复杂的数据库查询或加载完整的网页。

并发数：系统同时能处理的请求数量

吞吐量：指标参数有 QPS/TPS、RT、并发数。系统的吞吐量（承压能力）和 处理对 CPU 的消耗、外部接口、IO 等因素 紧密关联

- 并发数 = QPS x RT

## 说说印象最深刻的一个 bug

这个答案需要结合你简历中的项目。找一个模块，并为其设想一个 bug，这个 bug 不能很简单，比如是 Ui 错误、常见的功能问题。需要是比较难以发现的 bug，而且这个 bug 最好是对整体质量有一些影响，但是又不能表现出是测试的锅。

比如可以是一个功能测试环境是好的，但是上线时因为开发修改了配置导致的问题，让你记忆深刻。由此你也可以总结出每次上线后都会对配置进行检查。做好回归测试，防止类似问题再发生。

### 敏捷模型和瀑布模型

敏捷模型：基于迭代开发的软件开发方法。核心是将一个项目拆分成多个子项目，每个迭代周期完成一个子项目

### 三角形三边测试

-**有效等价类**：

- 普通三角形（三边均不等，且满足条件）。

- 边长为 0 或负数。
- 不满足三角形条件（如 1 2 4)。
- 构成退化三角形（两边之和等于第三边，如 1 2 3)。
- 非数值输入或数据类型错误。

## 说说排查问题的思路

排查问题的思路是：

2. 然后开始寻找问题复现的规律，看在什么情况下，该问题是毕现的。

## 说说什么是 CI/CD

持续集成和持续交付/部署(CI/CD)：在应用[开发阶段](https://zhida.zhihu.com/search?content_id=213750914&content_type=Article&match_order=1&q=开发阶段&zhida_source=entity)引入自动化来频繁向客户交付应用的方法

- 持续集成：新提交代码在合并前，需要先进行自动化测试。即，在源代码变更后自动检测、拉取、构建和（在大多数情况下）进行单元测试的过程，尽早发现问题
- 持续交付：完成自动化测试后，自动部署到测试环境，可以随时一键发布到生产环境，生产发布仍需人工确认
- 持续部署：持续交付的更高阶，代码通过自动化测试后，自动部署到生产环境，无需人工确认

核心价值：

1. 降低人为操作错误
2. 提升交付频率
3. 提高系统稳定性
4. 缩短反馈周期
5. 支持 DevOps 文化

DevOps（开发和运维协作） 是文化与理念，CI/CD 是落地工具。

## 某个用户网页打不开，如何定位问题

访问网页的流程：客户端 → 本地网络 → DNS → 运营商 → 服务器 → 应用程序

1、试试其他网站是否可以打开，如果也打不开，那么就是本机的网络问题，可以联系公司 IT 人员解决。

2、如果其他网站可以打开，那么就可以判定，应该是被测试网站的问题了，这个时候可以通过 ping 命令，ping 网站的域名：

- 如果不能解析 IP，可能是 **DNS 问题**，更换 DNS，检查 DNS 域名解析服务器有没有配置好。
- 如果 ping 不通，可能是**网络故障**、防火墙拦截

3、如果域名可以 ping 通，可能是网站**服务器宕机**，这个时候需要登录网站服务器，使用 netstat 命令查看 80 端口有没有启动，如果没有启动，需要启动 80 端口后面对应的服务器软件，比如：httpd 或者 tomcat 等。

4、如果 80 端口处于监听状态的，那么这个时候需要查看服务器的日志文件，进一步从日志上面进行分析。

5、应用层可能出现的问题有：数据库连接失败、Redis 不可用、配置错误、发布版本有 bug

表现可能是：500 错误、502 错误、504 超时

特殊情况

1. 只有某个用户打不开

可能原因：用户 IP 被封、地区限制、浏览器缓存问题、账号权限问题

2. 只有公司网络打不开

可能：、公司防火墙、代理问题

3. HTTPS 报错

可能：证书过期、证书不匹配、本机时间错误

## 缓存机制，如何测试

- 首先验证缓存是否生效，例如第一次请求从数据库读取，第二次请求从缓存读取，响应时间明显降低。
- 其次测试缓存更新机制，当数据发生变化时，缓存是否同步更新或删除。
- 第三是缓存过期测试，验证缓存到期后系统是否重新从数据库读取并生成新的缓存。
- 另外还需要测试高并发场景，例如缓存击穿、缓存雪崩和缓存穿透，验证系统是否有保护机制。
- 最后还需要验证缓存与数据库的数据一致性，以及在缓存服务异常时系统是否能够正常回退到数据库查询。

PO 模型简单来说：就是通过面向对象的方式，对**页面定位**和**页面操作**进行分离封装（解耦合，方便后续维护）。

## Selenium 定位元素的 8 种方式

1. id.
2. class_name.
3. name.
4. link_text.
5. partial_link_text.
6. tag_name.
7. css_selector.
8. XPath.

1、2、3：元素属性，不是所有元素都有，还有可能是动态的，通常跟 7、8 去组合使用比较多。

4、5：是用可点击的链接的文本去定位。**partial_link_text**也是根据可点击的链接的文本去定位，但这是文本的模糊匹配，只要包含有关键字就可以匹配

6：是根据元素标签名去定位。

7、8：最常用的方式，能结合前面 6 种方式组合去定位。7 是根据 css 选择器定位元素，8 是根据元素路径定位
