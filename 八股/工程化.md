## 模块化规范的演进

最原始的方式：所有 JS 文件通过 `<script>` 标签引入，全局变量污染，依赖顺序靠人工维护
CommonJS：require / module.exports，Node.js 的模块规范，同步加载，运行时加载，服务端使用为主
AMD / CMD：代表为 require.js，解决浏览器端的依赖管理问题，异步加载
UMD：兼容 CommonJS 和 AMD 的写法，目的是一个文件同时跑在浏览器和 Node
ES Module：ES6推出的JS原生支持的模块系统，import / export，现代浏览器的标准方案，编译时加载，静态分析友好，支持 tree shaking

## 构建工具到底解决了什么问题

从“手写 `<script>` 标签”到“写 import 跑 npm run build”，构建工具本质上在做：

- 模块**打包**：把分散的模块按依赖关系打包成浏览器能加载的文件
- 代码转译：ES6+ 语法转成 ES5（Babel）、TypeScript 编译、SCSS 转 CSS
- 资源处理：图片压缩、CSS 前缀补全、HTML 模板处理
- 开发提效：热更新、代理转发、代码检查

以目前最热门的构建工具 Vite 来说，Vite 本身会做很多事情，其中的打包则是透过 esbuild 与 Rollup 来处理（未来会改由 Rolldown 处理）。

为什么需要构建工具：

- 开发者体验：可以用vue、typescript、es6进行开发，vite的热更新使得页面更新速度快，开发体验好
- 兼容性：代码需要在浏览器上运行，需要构建工具转译成ES5、CSS等
- 模块化开发：开发者可以基于esm开发，构建工具会将有依赖关系的模块打包成一个文件，减少文件数量
- 性能优化：通过打包，利用树摇、代码分割、压缩等方式，减少包的体积，使得加载速度更快

### 打包

打包是构建工具从入口文件出发，分析模块依赖，生成依赖图后，对模块进行编译、转换、压缩和资源优化，最终输出浏览器可高效加载的静态资源。

通俗来说，打包就是根据依赖图，把不同的模块包在一起，将多个源文件合并成一个或少数几个文件，且尽量减少包的体积。这样能减少http请求的次数，实现按需加载。



## Webpack vs Vite——核心区别与选型

webpack在项目启动前会进行全量编译，即静态分析所有模块，生成依赖图，一次性编译、打包成最终文件。

vite使用esm，根据浏览器的请求来实时编译并提供源码，不会一次性全部打包好。

速度：

- 无论是冷启动还是热更新，vite由于采用按需编译的策略，速度更快
- webpack则会进行全量构建，速度稍慢

插件：

- 相对vite，webpack的插件生态丰富，可以满足更复杂的打包和优化需求

配置：

- webpack配置复杂，但功能也更强大，适合需要高度定制化的构建流程的项目，需要一定学习成本
- vite开箱即用，配置简单，适合快速构建项目

兼容性：

- webpack通过各种插件能更好地支持旧版浏览器

选型：

- vite适合基于ESM的现代项目、需要快速交付的项目
- webpack适合传统大型项目、需要深度构建构建流程的项目

以 Vite + Vue3 为例：

```
源码
├── src/
│   ├── main.ts
│   ├── App.vue
│   └── components/
├── index.html
└── vite.config.ts
```

**Vite 构建流程**：

```
1. 读取 vite.config.ts，确定入口、插件、构建目标

2. 依赖预构建（仅开发环境）
   node_modules 中的 CJS 模块 → ESM 格式
   原因：浏览器只认 ESM，lodash 等库是 CJS

3. 插件流水线处理每个模块
   .vue  → @vitejs/plugin-vue  → JS + CSS
   .ts   → esbuild             → JS（类型擦除）
   .scss → sass → postcss      → CSS
   图片  → 压缩/base64内联

4. Rollup 打包
   ├── 分析模块依赖图
   ├── Tree-shaking（删除未使用代码）
   ├── 代码分割（动态import → 独立chunk）
   └── 生成产物
```

**产物结构**：

```
dist/
├── index.html                     # 入口，注入了 script/link 标签
├── assets/
│   ├── main.a1b2c3d4.js          # 主入口 chunk
│   ├── vendor.e5f6g7h8.js        # 第三方库 chunk
│   ├── Dashboard.i9j0k1l2.js     # 懒加载路由 chunk
│   ├── main.m3n4o5p6.css         # 样式
│   └── logo.q7r8s9t0.png         # 静态资源（contenthash）
```

**index.html 最终长这样**：

```html

<html>
<head>
  <!-- 预加载关键 chunk -->
  <link rel="modulepreload" href="/assets/main.a1b2c3d4.js" />
  <link rel="stylesheet" href="/assets/main.m3n4o5p6.css" />
</head>
<body>
  <div id="app"></div>
  <!-- type="module" 告诉浏览器用 ESM 解析 -->
  <script type="module" src="/assets/main.a1b2c3d4.js"></script>

</html>
```

```
CDN 节点（全球分布）
```

**Nginx 配置**（对应缓存策略）：

```nginx
server {
  # HTML：不缓存，每次协商
  location ~* \.html$ {
    add_header Cache-Control "no-cache";
  }

  # 带 contenthash 的静态资源：强缓存一年
  location ~* \.(js|css|png|woff2)$ {
    add_header Cache-Control "max-age=31536000, immutable";
  }

  # 单页应用：所有路由指向 index.html
  location / {
    try_files $uri $uri/ /index.html;
  }
}
```

后续资源请求

浏览器拿到 HTML 后，解析到 `<link>` 和 `<script>` 标签，发起更多请求：

```
index.html
    ↓ 解析
    ├── /assets/main.css      → 请求 CDN（可能命中缓存）
    ├── /assets/main.js       → 请求 CDN
    └── /assets/vendor.js     → 请求 CDN

CDN 处理逻辑：
    ├── 命中 CDN 缓存  → 直接返回，不回源  ← 最快
    └── 未命中        → 回源到 Nginx 服务器

                         └── 未命中          → 返回文件
```

**HTTP/2 的影响**：

```
HTTP/1.1                   HTTP/2
────────────────────       ────────────────────
每个请求独占连接            多路复用，一个连接并发
串行或有限并行（6个）        真正并行，无队头阻塞
Header 每次完整传输         Header 压缩（HPACK）
```

四、浏览器解析渲染阶段

拿到资源后，浏览器开始渲染：

构建 DOM 和 CSSOM

```
HTML 字节流
    ↓ 编码解析
  字符流
    ↓ 词法分析（Tokenization）
  Token（标签/文本/属性）
    ↓ 语法分析
  DOM Tree

CSS 字节流 → CSSOM Tree（同步进行）
```

**JS 会阻塞 DOM 解析**：

```html
<script src="main.js"></script>
<!-- 浏览器必须等 JS 下载并执行完，才继续解析后面的 HTML -->

<!-- 解决方案 -->
<script defer src="main.js"></script>   <!-- 异步下载，HTML 解析完后执行 -->
<script async src="main.js"></script>   <!-- 异步下载，下载完立即执行 -->
<script type="module" src="main.js"></script>  <!-- 默认 defer 行为 -->
```

渲染树 → 布局 → 绘制

```
DOM Tree + CSSOM Tree
        ↓
   Render Tree（只含可见节点，display:none 不在其中）
        ↓
   Layout（回流）：计算每个节点的几何信息
        ↓
   Paint（重绘）：生成绘制指令
        ↓
   Composite：合成层合并，送 GPU 输出到屏幕
```


| 阶段   | 问题               | 优化手段                       |
| ------ | ------------------ | ------------------------------ |
| 构建   | bundle 太大        | Tree-shaking、代码分割、懒加载 |
| 部署   | 资源更新用户不感知 | contenthash + 强缓存           |
| DNS    | 解析慢             | DNS prefetch、减少域名数       |
| 连接   | 握手耗时           | preconnect、HTTP/2、keep-alive |
| 传输   | 体积大             | gzip/brotli、图片压缩、CDN     |
| 解析   | JS 阻塞渲染        | defer/async、关键CSS内联       |
| 渲染   | 白屏时间长         | SSR、骨架屏、preload关键资源   |
| 运行时 | 交互卡顿           | 虚拟列表、防抖节流、Web Worker |



## 讲讲 tree-shaking

> Tree-Shaking 是一种基于 ES Module 规范的 Dead Code Elimination 技术，它会在运行过程中静态分析模块之间的导入导出，确定 ESM 模块中哪些导出值未曾其它模块使用，并将其删除，以此实现打包产物的优化。

1、实现tree-shaking的条件需满足如下条件：基于 **ESM** 的导入导出规则，可以实现静态编译时处理模块间的依赖
2、tree-shaking 的删除过程类似于js 的垃圾收集：分析 -> 标记 -> 清除



ESM规范：

- 所有的导入导出语句只能出现在**模块顶层**，且导入导出的模块名必须为字符串常量
- 所以，ESM 下模块之间的依赖关系是高度确定的，与运行状态无关，编译工具只需要对 ESM 模块做静态分析，就可以从代码字面量中推断出哪些模块值未曾被其它模块使用，这是实现 Tree Shaking 技术的必要条件。

tree-shaking举例：

```js
// index.js
import {bar} from './bar';
console.log(bar);

// bar.js
export const bar = 'bar';
export const foo = 'foo';
```

示例中，`bar.js` 模块导出了 `bar` 、`foo` ，但只有 `bar` 导出值被其它模块使用，经过 Tree Shaking 处理后，`foo` 变量会被视作无用代码删除。



tree-shaking的最佳实践：

- 避免**无意义的赋值**导致 Webpack 不能检测到没有真正被使用的export
- 用`#pure`标记的纯函数调用可以被 Tree Shaking 删除
- 禁止 Babel 转译模块导入导出语句成 CommonJS 风格
- 优化导出值的粒度和原子性

### tree-shaking实现原理

步骤：

- 收集模块导出，标记出没有被使用过的export
- 用Terser删除



具体步骤：

- 在 `FlagDependencyExportsPlugin` 插件中根据模块的 `dependencies` 列表收集模块导出值，并记录到 ModuleGraph 体系的 `exportsInfo` 中
- 在 `FlagDependencyUsagePlugin` 插件中收集模块的导出值的使用情况，并记录到 `exportInfo._usedInRuntime` 集合中
- 在 `HarmonyExportXXXDependency.Template.apply` 方法中根据导出值的使用情况生成不同的导出语句
- 使用 DCE 工具（Terser）删除 Dead Code，实现完整的树摇效果



#### 具体实现

1. 收集模块导出

- 将模块的所有 ESM 导出语句转换为  `HarmonyExportXXXDependency` 类型的 Dependency 对象，并记录到 `module` 对象的 `dependencies` 集合
- 所有模块都编译完毕后，触发 `compilation.hooks.finishModules` 钩子，开始执行 `FlagDependencyExportsPlugin` 插件回调
- `FlagDependencyExportsPlugin` 插件从 entry 开始读取 ModuleGraph 中存储的模块信息，遍历所有 `module` 对象
- 遍历 `module` 对象的 `dependencies` 数组，找到所有 `HarmonyExportXXXDependency` 类型的依赖对象，将其转换为 `ExportInfo` 对象并记录到 ModuleGraph 体系中



2. 标记模块导出

- 触发 `compilation.hooks.optimizeDependencies` 钩子，开始执行 `FlagDependencyUsagePlugin` 插件逻辑
- 在 `FlagDependencyUsagePlugin` 插件中，从 entry 开始逐步遍历 ModuleGraph 存储的所有 `module` 对象
- 遍历 `module` 对象对应的 `exportInfo` 数组
- 为每一个 `exportInfo` 对象执行 `compilation.getDependencyReferencedExports` 方法，确定其对应的 `dependency` 对象有否被其它模块使用
- 被任意模块使用到的导出值，调用 `exportInfo.setUsedConditionally` 方法将其标记为已被使用。
- `exportInfo.setUsedConditionally` 内部修改 `exportInfo._usedInRuntime` 属性，记录该导出被如何使用



3. 生成代码

经过前面的收集与标记步骤后，Webpack 已经在 ModuleGraph 体系中清楚地记录了每个模块都导出了哪些值，每个导出值又没那块模块所使用。接下来，Webpack 会根据导出值的使用情况生成不同的代码

4. 删除 Dead Code

经过前面几步操作之后，模块导出列表中未被使用的值都不会定义在 `__webpack_exports__` 对象中，形成一段不可能被执行的 Dead Code 效果，由 Terser、UglifyJS 等 DCE 工具“摇”掉这部分无效代码

# webpack

## 什么是webpack

Webpack中一些术语：

- **Entry Points：**构建流程的入口，它决定了Webpack从哪里模块开始构建。
- **Compiler：**Webpack的编译器，通常情况一个构建流程中只有一个Compiler，直至退出构建程序。
- **Compilation：**也是Webpack的编译器，但它是每次编译都会实例化一次新的Compilation，比如watch模式下会有多次编译的情况。
- **Hooks：**Webpack的一些任务需要「外包」出去，Hooks是通知或接收消息的通道，核心实现是[Tapable](https://link.zhihu.com/?target=https%3A//github.com/webpack/tapable)库，下文把Hooks统称为「钩子」。
- **Module：**在Webpack中，Javascript代码或图片视频等静态资源都算模块。
- **Chunk：**比Module粒度更大的「块」，可以组合成Bundle，有两种形式的Chunk，一种是Entry Points对应的Chunk，另外一种是Dynamic Imports或Code-Splitting产生的Chunk。
- **Bundle：**源代码文件在经过加载和编译处理和优化之后的最终产物。

## webpack打包原理

1. 识别入口文件
2. 通过逐层识别模块依赖(Commonjs、amd或者es6的import，webpack都会对其进行分析，来获取代码的依赖)
3. webpack做的就是分析代码，转换代码，编译代码，输出代码
4. 最终形成打包后的代码

## webpack 性能优化有哪些方法

分类：

- 优化一：打包后的结果，上线时的性能优化。（比如分包处理、减小包体积、CDN服务器等）
- 优化二：优化打包速度，开发或者构建时优化打包速度。（比如exclude、cache-loader等）

这里侧重于优化一，即打包后性能优化

1. **代码分离**

将代码分离到不同的包中，之后可以按需加载

- 入口起点：使用entry配置多入口，并共享依赖
- 动态导入：用import导入需要的模块。可设置预获取和预加载
  - prefetch(预获取)：将来某些导航下可能需要的资源
  - preload(预加载)：当前导航下可能需要资源
- 用SplitChunks自定义分包，例如指定拆分包的大小、将runtime相关的代码单独抽取出



2. **CDN服务器**

## webpack 的 loader 和 plugin 区别是什么？常用的 plugin 和 loader 有哪些

loader：一个转换器，将A文件进行编译成B文件。比如将A.less转换为A.css。是单纯的文件转换过程。因为webpack自身只支持js和json这两种格式的文件，对于其他文件，需要通过loader将其转换为commonJS规范的文件后，webpack才能解析到。

常用loader：css-loader、style-loader、postcss-loader、sass-loader

plugin：一个扩展器，它丰富了webpack本身，针对是loader结束后，webpack打包的整个过程，它并不直接操作文件，而是基于事件机制工作，会监听webpack打包过程中的某些节点，执行任务，比如资源管理、bundle文件优化、压缩等

常用plugin：SplitChunksPlugin（自定义分包）、mini-css-extract-plugin（提取css）、css-minimizer-webpack-plugin（压缩CSS）



## webpack 构建流程是什么

Webpack的构建流程主要分成四个环节，即**CLI初始化（webpack.config.js）**、**编译模块（Compiler）**、**打包模块（Compilation）**和**产物输出。**

1. CLI初始化

Webpack则是把相关构建指令实现拆分了出去，交给另外单独的npm模块（webpack-cli），完成CLI的初始化和创建Compiler ，以及确定构建的配置信息

2. 编译

编译阶段：从解析Entry Points开始，直至构建完整的模块依赖图（Module Graph）

Entry Points是定义模块依赖图的起始点，确定Entry Point后，递归解析依赖，构建模块依赖图

3. 打包

将上述模块重新组装成Bundle或生成静态资源

4. 生成assets

先对模块进行处理，生成Webpack Source，再使用RuntimeTemplate及sourceAndMap方法生成对应的Runtime代码
