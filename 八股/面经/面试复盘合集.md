10. 做这些项目的目的是什么？

工程化思维

后台管理系统是我做的第一个完整业务型项目，在开发过程中发现很多 UI 和逻辑是重复的，比如表单、弹窗、表格这些组件在多个页面都会用到。

如果每个页面都重新实现，会带来两个问题：一是代码重复度高，二是后续修改成本很大。

所以我把这些通用能力逐步抽离成独立组件，并进一步整理成组件库。这样做的目标是把“业务页面”和“通用能力”解耦，提升复用性和可维护性。

同时组件库的设计也让我更关注边界条件处理、props 设计和组件的开放/封闭原则，比如尽量只暴露必要配置，内部封装复杂逻辑。

11. 后台系统是怎么设计的？是自己设计的，还是有参照？

这个项目整体是参考了一些开源后台模板的结构设计，比如权限系统和路由结构

我主要做了两点调整：
第一是权限模型简化，只保留角色维度的权限控制，减少复杂度；
第二是把路由和权限做了前端动态生成处理，方便根据用户权限动态控制菜单和页面访问。

同时在权限、用户、表单这些模块之间做了基础的分层，尽量保证页面只处理展示逻辑，业务逻辑集中在 API 和 store 层。

1.  动态路由是什么意思？你是怎么实现动态路由的？

动态路由主要是基于用户权限控制页面访问范围。

登录后后端会返回当前用户的权限信息，其中包含可访问的路由标识列表。

前端在拿到这个列表后，会和本地的路由配置做一次过滤，只保留用户有权限的路由，然后通过 Vue Router 的 addRoute 动态注册进去。

这样可以实现不同角色登录后看到不同菜单，并且在路由层面直接限制访问。

1.  服务端和前端是同一个工程吗？

不是同一个工程，是前后端分离的结构。

后端是基于一个开源项目独立跑起来的服务，前端是单独的 Vue 工程，通过 HTTP 接口进行数据交互。

我这边主要是按照后端提供的接口文档进行开发，同时在项目过程中也参与了一部分接口字段的约定，比如用户信息结构、权限列表、路由数据格式这些。

在开发过程中前后端是通过接口约定来对齐数据，而不是放在同一个工程里。

15. 会出现跨域吗？你是怎么解决跨域的？

是跨域的。虽然前后端都在本机，但前端和后端分别运行在不同端口上，本质上属于不同源，所以会触发浏览器的同源策略限制。

我在开发环境主要使用 Vite 的 proxy 做了代理转发。
前端请求先发到本地 dev server，再由 dev server 转发到 Docker 中运行的后端服务，这样可以避免浏览器直接跨域请求。

生产环境的话一般会换成 Nginx 或网关层做反向代理。

16. 除了 Vite proxy / 代理，还有哪些跨域解决方案？

跨域常见的解决方案主要有几类：

第一类是服务端解决，比如 CORS，在响应头里配置允许的源，这是最标准的方式。

第二类是代理方式，比如开发环境的 Vite proxy 或生产环境的 Nginx 反向代理，本质是把跨域变成同源请求。

第三类是 JSONP，但它只适用于 GET 请求，现在基本很少用了。

另外还有一些跨窗口方案比如 postMessage，用于不同页面之间通信。

18. nextTick 的底层原理是什么？

Vue 的 nextTick 是用来在 DOM 更新完成之后执行回调的。

因为 Vue 的响应式更新是异步的，它不会在数据变化后立即更新 DOM，而是把多次数据变更合并成一次更新（批处理）。

nextTick 的作用就是把用户的回调延迟到这次 DOM 更新结束之后执行，这样就可以获取到更新后的真实 DOM。

在底层实现上，Vue 会根据环境优先使用 Promise.then 这类 微任务，如果不支持则降级为 MutationObserver 或 setTimeout，本质是利用异步队列把回调延后执行。

19. 能讲一下 Tree-shaking 的过程吗？

Tree shaking 是一种通过静态分析移除未使用代码的优化手段，通常在基于 ES Module 的环境中生效。

因为 ESM 的 import/export 是静态结构，打包工具（如 Rollup / Vite / Webpack）可以在编译阶段构建依赖图，分析哪些导出被实际使用。

对于没有被引用的 export，会被标记为 dead code，在压缩阶段被移除，从而减少最终 bundle 体积。

但 tree shaking 生效有前提，比如模块不能有明显副作用，否则工具无法安全删除代码。

所以在 package.json 里一般会通过 sideEffects 字段告诉打包工具哪些文件可以安全删除。

22. 以 Form 表单为例，讲一下你的设计思路。

大致拆成 Form 和 FormItem 两层结构。

Form 负责统一管理表单数据和校验逻辑，FormItem 负责具体字段的展示和校验规则绑定。

在数据通信上，我使用 provide / inject，把 Form 实例注入给所有 FormItem。FormItem 在初始化时会向 Form 进行注册，把自己的字段 key 和校验函数注册进去。

Form 内部维护一个字段列表，当调用整体校验时，会遍历所有已注册的字段，统一执行校验函数，从而实现全表单校验能力。

在校验设计上，支持单字段校验和整体校验两种模式，同时支持自定义校验规则，比如 required、pattern 或自定义 validator。

另外在类型层面，我用 TypeScript 对 Form 数据结构和校验规则做了约束，这样在使用时可以有完整的类型提示，减少误用。
